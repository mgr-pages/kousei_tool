# 照合中のメモリを 1024MB 以内に抑える（2026年11月27日）

依頼：校正（照合）中に使うメモリの量に上限を設ける。PC は 1024MB が目安。スマホは不明。

## 1. 調べたこと

- ブラウザのページから、使えるメモリの量を決める方法はない。使っている量を正しく測る方法（`performance.measureUserAgentSpecificMemory()`）は、サーバーで特別な設定（クロスオリジン分離）をしたページでしか使えず、GitHub Pages・手元で開く HTML では使えない。Chrome だけの `performance.memory` は JS の領域だけで、画像などの大きなデータを数えない（照合中も 82〜141MB しか示さなかった）
- そのため、ツールの側で使う量を抑える作りにし、ブラウザの外から（プロセスの実メモリ PSS で）測って確かめた
- スマホ：iOS の Safari には canvas（画像を描く所）の合計の上限があり、224〜384MB と報告されている（iOS の版・機種で違う）。ページ全体の上限（超えるとページが読み込み直される）も機種で違い、公式の値は見当たらない（不明）

## 2. 直す前の実測（Chromium。ブラウザの全プロセスの PSS）

実データ（A3見開き相当 2ページ・画像の多いページ。旧版との比べ合わせ・OCR あり）：

| | 照合中の最大 | 照合のあと |
|---|---|---|
| ブラウザ全体 | 1,991〜2,029MB | 1,903〜1,914MB |
| うちページのプロセス | 1,880〜1,919MB | |

（同じ照合でも、ごみ集めの時期によって測るたびに 100MB ほど揺れる。2回の測定の幅で示す）

照合のあとに残っていたものの内訳（順に手放して測った）：ごみ集め待ちの画像など 約400MB → OCR の部品 約100MB → PDF の読み込み部品（pdf.js）が抱えていた展開済みの画像など 約600MB。

## 3. 直したこと

| 直したこと | ねらい |
|---|---|
| 描いたページの画像（canvas）を、使い終わったらすぐ空にする | ごみ集めを待つと、大きなページで何百MBもたまる |
| pdf.js がページのために展開した画像などを、描くたびと照合の段階ごとに手放す（`page.cleanup`・`doc.cleanup`） | 画像の多いページで何百MBもたまる |
| OCR の部品を、ページごとに読み終えたら閉じる | 読んだ画像に合わせて広げたメモリを手放さない |
| 照合が終わったら（途中でやめたときも）、開いた PDF と OCR の部品を閉じる | 結果の表示に PDF は要らない |
| 表示用の縮めた画像を、もとの大きさの写しを作らずに作る | 1枚ごとに 100MB 以上の写しを作っていた |
| 成果物だけで見るチェックの辞書を、使い終わったら手放す（照合のたびに読み込み直す。1秒ほど） | 約134MB（測った値）を持ち続けていた |
| ページの対応づけ・旧版との比べ合わせの中でも、1ページごとに pdf.js の展開した画像などを手放す | 段階の切れ目までたまっていた |
| A3見開き（200dpi で 1050万画素）より大きいページは、照合の前に知らせる | 上限の目安を超えることがあるため |

## 4. 直したあとの実測（ページのプロセスの最大。1回の照合）

| 照合 | ページのプロセスの最大 | ブラウザ全体の最大 | 照合の時間 |
|---|---|---|---|
| 実データ A3見開き 2ページ・旧版あり・OCR あり | **905〜920MB**（2回測った。直す前 1,880MB） | 1,013〜1,028MB | 93〜95秒（直す前 61秒。同じ条件で続けて測った） |
| テスト用 A4 4ページ・紙のスキャン原稿 | 927MB | 1,031MB | 45秒 |
| テスト用 A4 4ページ・注釈PDF | 649MB | 753MB | 16秒 |
| テスト用 紙の赤字原稿＋旧版 | 661MB | 764MB | 8秒 |
| テスト用 レイアウトが違う原稿＋旧版 | 615MB | 728MB | 6秒 |

- ページを開いただけで、ページのプロセスは約280MB（埋め込んだ部品：PDF・画像処理・OCR・辞書）
- 画像の多いページでは、同じページを描き直すたびに画像を展開し直すので、照合が5割ほど遅くなった（実データ：61秒 → 93秒）。画像の少ないページ（テスト一式）では、ほとんど変わらない
- 同じページで続けて照合すると、2回目は上限を超えることがある（実データ A3見開き 2ページ：1回目 873MB・2回目 1,166MB。スキャン原稿：2回目 約1.3GB）。ブラウザが、手放したメモリの一部を、PCのメモリに余裕があるあいだ作業用の置き場として持ち続けるため。メモリ不足の合図（`Memory.simulatePressureNotification`）を送ると、約400MB がすぐ減った（漏れではない）。ツールからは、ブラウザにこの置き場を手放させる方法がない

## 5. 残っている課題

- 同じページで続けて照合したときの2回目（上の段落）。大きな作業用の配列を使い回す作りにすれば減らせる見込み（推測：数時間の作り直し）
- 画像の多いページで照合が遅くなった（メモリと時間の引き換え）
- A3見開きより大きいページ（B2ポスターなど）は、上限の目安を超えることがある（知らせるだけで、照合はそのまま行う）
- スマホの上限の値（端末・ブラウザで違い、実機で確かめていない）
- 測ったのは Chromium（PC）だけ。Edge は同じ部品（Chromium）なので同じ傾向と見込むが、確かめていない
